# Render deployment — prepared, not yet published

This repository includes a `render.yaml` Blueprint for one Node web service that serves the Vite build and Express API together. SQLite lives on a 1 GB persistent disk at `/var/data/money-runway.sqlite`. It does not need a separate static-site service or an external database.

## Deployment prerequisites

1. A connected Render account/workspace.
2. A GitHub/GitLab/Bitbucket repository containing the current source, package lock, `render.yaml`, `public/`, and documentation. This local folder currently has no Git remote; no deployed URL exists yet.
3. Review the paid compute and disk cost shown in Render before approving creation. The Blueprint uses plan `0.5c-512mb` plus a 1 GB persistent disk. Do not silently substitute a free ephemeral filesystem: it would lose SQLite data across restarts/redeploys. Sponsor credits, if available on your account, do not remove the need to review billing.
4. Backend Sandbox client ID/secret and Sandbox business email entered through Render's private environment settings. Never commit `.env` or put those values into `render.yaml`.

Sources: [Render Express deployment](https://render.com/docs/deploy-node-express-app), [Blueprint specification](https://render.com/docs/blueprint-spec), [persistent disks](https://render.com/docs/disks).

## Concrete service configuration

| Setting | Value |
| --- | --- |
| Runtime | Node.js 24.19.0 |
| Build | `npm ci --include=dev && npm run build` |
| Start | `npm start` |
| Health check | `/api/health` |
| Bind address | `0.0.0.0` on Render-provided `PORT` |
| Disk mount | `/var/data` |
| Database | `/var/data/money-runway.sqlite` |
| Instances | 1, required for local SQLite |
| Automatic deployment | Off, preserve a controlled submitted build |
| Demo seed | `2026-11-10`, only on a fresh database |
| Judge username | `judge` |
| Judge password | Generated by Render; retrieve privately from its environment settings |

The runtime seeds only when needed; a deploy/restart never resets an existing database. The Blueprint pins the first demo to November 10 to reproduce the ₹300 and delayed-income scenario. Later demo-date changes persist in SQLite.

## Protected judge access

Production refuses to start without a non-placeholder `DEMO_PASSWORD` of at least 16 characters. All pages/API routes are behind browser Basic authentication except the minimal public health endpoint. This is a password-protected single-profile hackathon demo, not a multi-user banking product. Give judges the username/password in the submission's private testing instructions; do not publish them in the public README or video.

The browser uses the HTTPS origin supplied by `RENDER_EXTERNAL_URL`. Same-origin writes work behind Render's proxy; other browser origins are rejected. If you add a custom domain, set `APP_ORIGIN=https://your-domain.example`. No permissive wildcard CORS is enabled. Postman uses Basic authentication and normally sends no Origin header.

Optional `OPENAI_API_KEY` can be added after creation; `OPENAI_MODEL` defaults to the existing app model. Missing AI credentials leave explicit deterministic fallback mode. Actual model verification requires a model response, not fallback. Changing environment variables requires a deploy/restart.

No local `.env`, existing SQLite data or exposed login password is uploaded by the Blueprint. First deployment creates a fresh seeded database. If demonstrating live Sandbox activity online, sync through the protected backend after configuring its environment.

## Create and verify

In Render: **New → Blueprint**, connect the repository, choose the branch containing `render.yaml`, review the proposed service/disk and costs, enter requested Sandbox environment values, then approve creation. When using the connected Render integration, first create/plan the Blueprint, review its returned plan, and approve only after the user authorizes that concrete plan.

After deployment:

1. Check the deploy reports `live` and `/api/health` returns `{"status":"ok","app":"Money Runway"}`.
2. Open the service URL, sign in with the judge credentials and check Today/Planner/Calendar.
3. Import the checked-in Postman collection. Set `baseUrl` to this HTTPS URL and set judge credentials only in local values. Keep mutations disabled for a shared demo.
4. Verify an expense saved through the browser survives refresh and a controlled restart. Do not delete or replace the disk between deploys.
5. Enable optional live PayPal/AI checks only when credentials are configured. Record successful live results and keep secrets out of the video.
6. Supply judges with the URL and protected test-access instructions. Preserve access through judging.

No real invoice draft is automatically created during deployment or testing. The app's explicit invoice review/approval flow remains separate.

## Local production smoke check

Use a fresh temporary database and an owner-only temporary environment if needed; do not reuse the real profile for mutation checks. For an interactive production-like local run:

```sh
npm run build
NODE_ENV=production HOST=127.0.0.1 PORT=3002 DEMO_USERNAME=judge DEMO_PASSWORD=REPLACE_WITH_A_RANDOM_16_PLUS_CHARACTER_PASSWORD APP_ORIGIN=http://127.0.0.1:3002 DATABASE_PATH=./data/production-smoke.sqlite DEMO_SEED_DATE=2026-11-10 npm start
```

The password above is an obvious placeholder and must be replaced locally; it is not a supplied judge credential. For local normal development use `npm run dev`, which keeps the existing loopback/no-password defaults unless you configure a demo password.

Automated production smoke check:

```sh
npm run test:production
```

It builds the frontend, starts the real production entry point with a temporary database and synthetic judge password, verifies public health/protected HTML and API access, records a small expense through the allowed origin, restarts the entire process and confirms SQLite retained it. It clears integration credentials and does not touch the real `.env` profile.
